# 使用坚果云 / WebDAV 为网页和 Android APP 实现增量同步

版本：1.0，2026-10-19。目标读者：需要给其他应用编写同步模块的开发者或 IDE 编程代理。本指南以高效 ToDo 本地版 0.8.0 的已验证实现为参考，但不依赖待办业务。不要让其他应用直接使用本项目的正式云目录。

这是一套**应用层记录同步协议**：每台设备保有自己的数据库，把变更日志和恢复快照作为普通 WebDAV 文件传输。坚果云负责保存文件、HTTPS 传输和条件写；业务合并、冲突、接收进度和重试由应用负责。它不是把一个正在写入的 SQLite 文件分块共享给多台设备。

## 1. 使用范围与前提

适合离线优先的个人笔记、任务、资料索引、轻量业务记录。已用六个独立 SQLite 客户端连接真实坚果云验证交错写入，并让真实 Android APK 加入完成双向收发。实体设备数量、硬件和长期耗电仍要另测。

协议提供最终收敛：各设备最终联网、服务保存已确认文件、设备继续同步、同名设备身份不被克隆时，能够补齐已经发布的变化。一次“完成”只针对该轮最后读到的清单，不能承诺永久离线设备、后来发生的写入也已实时到达。

不提供跨设备串行事务或服务器业务锁。库存扣减、支付余额、唯一名额等强一致业务需要服务端事务或专门的数据模型。普通字段寄存器也不能直接替代计数器、协作文档文本等专用合并算法。

信任模型是同一用户控制的多个客户端；HTTPS、ETag 和 SHA-256 不构成对恶意客户端的完整防护。本实现未对云端业务数据做端到端加密，应用密码仅在设备上加密保存。

## 2. 架构与平台选择

~~~mermaid
flowchart LR
  UI[业务界面] --> TX[本地原子事务]
  TX --> DB[实体表与字段版本]
  TX --> OUT[持久发件箱]
  OUT --> SYNC[同步引擎]
  SYNC <--> DAV[WebDAV 适配器]
  DAV <--> CLOUD[不可变批次 + 小清单 + 快照]
  SYNC --> RX[合并记录与保存接收进度的事务]
  RX --> DB
~~~

| 平台 | 推荐本地存储 / 网络实现 | 要点 |
| --- | --- | --- |
| 本机网页 + 本地服务 | SQLite + 本地 Node/其他服务代理 WebDAV | 本项目实际路径；Node 的内建 SQLite 需要 22.13+ |
| 纯浏览器网页 / PWA | IndexedDB，或支持的平台上使用 OPFS SQLite | 同样需要实体、版本、发件箱和元信息的原子事务；持久存储权限、配额、清除站点数据要另处理 |
| Android 原生 | SQLite/Room + 原生 HTTP 客户端 | 不在主线程执行数据库、压缩或网络任务；凭据用 Keystore |
| Android WebView / 混合 APP | 共享协议代码 + 原生 SQLite/HTTP 桥接 | 只把需要显示的数据送进 WebView；保存后不把密码原文回传给前端 |

纯网页不能假设跨域 WebDAV 一定可用。必须实测服务的 CORS 与预检；不可用时通过本地服务或受控后端代理。代理限制目的主机、方法、路径和请求体，不能成为任意 URL 转发器。不要把用户的应用密码发给未经授权的第三方代理。

所有业务读写必须绑定明确的本地账号 ID；云范围由“服务端点 + 云账号 + 应用目录 + 协议空间”确定。界面切账号不能改变已经在执行的事务所属账号。

## 3. 四种编号必须分清

| 名称 | 含义 | 是否相同 |
| --- | --- | --- |
| entityId | 某条业务记录的稳定 ID | 跨设备相同，不能用数组位置 |
| actor | 一个本地数据库副本的设备身份 | 不同数据库分别生成随机 UUID |
| event.seq / vector | 某 actor 的事件序号及因果上下文 | 描述修改的先后关系 |
| batch.index / cursors | 某 actor 的上传批次号及各来源已接收位置 | 描述哪些云文件已连续应用 |

一个批次可含多个事件，所以事件序号不等于批次号。不能用“最后同步时间”替代每个来源的接收游标；墙上时钟只用于显示、调度或租约，不决定业务修改谁覆盖谁。

一个账号数据库在同一电脑上被多个窗口使用时共享 actor，靠本地事务序列化。另一个账号数据库即使在同一电脑上，也应有自己的 actor。

不要把正在使用的数据库直接克隆到另一设备并继续沿用 actor；这会造成相同批次路径承载不同内容。新设备应创建空数据库和新身份，然后从云端加入。恢复很久以前的整机备份也要考虑 actor 序号倒退；应提供重新加入/身份恢复流程，不能强制覆盖云端同名文件。

## 4. 本地数据库设计

概念表结构如下，可映射为 SQLite 表或 IndexedDB 对象仓库。字段类型、业务索引按应用调整。

~~~sql
CREATE TABLE entities (
  key TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  id TEXT NOT NULL,
  data TEXT NOT NULL,
  versions TEXT NOT NULL,
  deleted INTEGER NOT NULL,
  conflicts TEXT NOT NULL
);
CREATE TABLE outbox (
  queue_id INTEGER PRIMARY KEY,
  event TEXT NOT NULL
);
CREATE TABLE sync_meta (
  id INTEGER PRIMARY KEY,
  actor TEXT NOT NULL,
  local_seq INTEGER NOT NULL,
  logical_clock INTEGER NOT NULL,
  revision INTEGER NOT NULL,
  data_revision INTEGER NOT NULL,
  scope TEXT,
  epoch TEXT,
  vector TEXT NOT NULL,
  cursors TEXT NOT NULL,
  pending_batch TEXT,
  cached_manifest TEXT,
  lease TEXT
);
~~~

本项目为便于跨平台桥接把元信息存在 meta.value JSON 中，把事件版本存在 entities.record；以上是概念上的展开。实体行中的部分字段可以使用 JSON，但索引、筛选、事务和按行更新由数据库承担，仍然不同于每次重写完整 JSON 数据文件。

需要建立实际业务索引。例如未删除/未完成/日期、提醒时间、父记录 ID。列表使用 LIMIT/分页，后台提醒只查相关记录，桌面组件只查需要显示的几行。不要换成 SQLite 后仍在每次点击时查询并序列化全部历史；本项目当前前端仍存在完整业务投影载入，这一部分不能当作所有应用的最终性能方案。

### 两类必须原子的事务

1. 本地修改：实体及字段版本 + 新事件 + outbox + 本地序号/逻辑时钟，一起提交。
2. 接收批次：实体及字段版本 + vector + 该来源连续接收游标，一起提交。

如果只保存了实体却没有发件箱，崩溃后改动不会上传；如果先推进游标再保存实体，崩溃后会永久跳过记录。不能把这些动作分散为互不关联的异步保存。

使用 revision 做本地比较并交换，失败后重新读取再计算。data_revision 仅在实体内容变化时递增，供快照一致性检查；续租、缓存清单等元信息变化不应误判为业务快照失效。

## 5. 变更与合并模型

以下是示意事件；其他应用要自行定义 kind 和字段。若要求直接兼容本项目线格式，必须遵守源码中固定的 kind、字段规范化及版本约束，不能只改一个 format 字符串。

~~~json
{
  "key": "[\"items\",\"item-123\"]",
  "actor": "device-a",
  "seq": 42,
  "clock": 109,
  "context": {"device-a": 41, "device-b": 27},
  "values": {"title": "修改后的标题"}
}
~~~

- 只发送实际变化字段；创建时带稳定 ID 和初始字段，删除用 _deleted=true。
- clock 是逻辑时钟：接收后至少达到已观察事件最大值，本地写入继续递增。
- context 表示该修改所依据的因果版本。对于用户打开后尚未看到新远端内容的草稿，应携带打开/读取草稿时的上下文，不应在保存瞬间偷偷换成最新数据库上下文。
- 同一 actor 的本地后续写入覆盖自己的先前事件。不同 actor 真正并发的同字段版本都保留；不同字段分别合并。
- 当前可显示一个确定的优先版本，但不能因此丢弃另一个并发版本。参考排序为逻辑时钟、actor、seq；移植到不同语言时要规定一致的比较规则，推荐统一小写 ASCII actor 和确定的字节序比较。
- 用户选择冲突版本时生成新的事件，其上下文覆盖所见冲突版本。不能直接在本地把另一份记录删掉，否则其他设备仍会重新带回冲突。

同字段版本的核心规则：新事件 context 覆盖某旧事件时，该旧事件对应字段被取代；旧事件的 context 覆盖新事件时，迟到的新字段已过时；两者互不覆盖时共同保留。记录保留当前仍有效的字段版本，不要求无限保留每次历史修改。

同一事件可能同时修改多个字段；快照中的该事件可能已经裁掉被后续事件取代的字段。因此不要把“已压缩版本中的事件片段”与“原始完整事件”的整份字符串相等作为唯一去重判断。不可变上传批次重试仍需比较文件完整内容，防止同名不同内容。

### 删除、字段移除和引用

删除标记参与合并，删除优先于并发旧副本的自动复活；恢复必须是明确的新事件。不能收到删除就物理删掉版本信息。

为新业务定义 null、字段缺席与字段删除的含义。当前项目先把业务对象规范化为固定字段，再比较差异；任意 JSON 模型需要另加 unset 语义，否则“字段不见了”可能永远不会传出去。

树状数据应拆成独立记录和 parentId。父记录删除或并发换父形成环时，应有可访问的兜底展示，不能让子记录消失在不可达树中。引用完整性、顺序、重复任务实例 ID、金额累加等属于业务层；同步引擎不会自动推导正确规则。

## 6. 云端文件布局与线格式

参考布局：

~~~text
<App>-<AccountScope>/
  state.json                      # 如需隔离旧协议，存升级标记
  v2/
    manifest.json                 # 小型可变清单，必须条件写
    b-<actor>-<index>.json.gz      # 不可变事件批次
    s-<snapshotId>-<part>.json.gz   # 不可变快照片段
    legacy-<uuid>.json.gz          # 可选的旧云端文件留存
~~~

清单示意：

~~~json
{
  "format": "myapp-delta",
  "version": 2,
  "epoch": "random-space-uuid",
  "heads": {"device-a": 12, "device-b": 8, "device-c": 3},
  "snapshot": null
}
~~~

epoch 标识一个同步空间世代。发现不一致要重新绑定/恢复，不得把旧 pending 批次改头换面写入新空间。format 与 version 在读入业务前校验；不认识的版本停止，不用空数据覆盖。

批次示意：

~~~json
{
  "format": "myapp-batch",
  "epoch": "random-space-uuid",
  "device": "device-a",
  "index": 12,
  "events": []
}
~~~

一个文件命名只对应一份确定内容。JSON 使用 UTF-8；计数和时钟限定在所有实现都能精确表示的整数范围内。哈希、空值、字符串、排序与序列化约定都要写入跨语言测试向量。

## 7. 一次同步的完整流程

~~~text
取得本地同步租约
读取清单（可以 If-None-Match）
必要时建立目录 / 初始化同步空间
绑定 scope + epoch
必要时合并完整快照
按各来源连续游标补批次
从持久 outbox 生成并保存 pending 批次
上传不可变批次
条件更新清单中的本 actor 进度
清单发布成功后确认并清除对应 outbox
根据最后观察到的清单再补远端变化
保存缓存、状态；可选生成快照
释放租约
~~~

### A. 拉取：按来源补齐，不用一个全局时间点

例如清单为 A=12、B=8、C=3，本地游标为 A=10、B=8、C=1，就分别获取 A11、A12、C2、C3。A 与 C 在同一个检查周期内先后写入也不会丢失。

读取单个来源的下一批，校验 epoch/device/index、大小及事件结构，合并并和游标一起提交。遇到缺失 A11，不能看到 A12 就直接推进到 12。已经应用的批次再次下载应可幂等重放。

不要使用无限制并发下载把旧手机内存占满。每轮限制批次/字节/时间，剩余工作持久化后在下一轮继续；界面要区分“本轮部分完成”和“补齐本次观察到的全部变化”。

### B. 推送：先上传批次，再登记清单

1. 在本地事务内保存 pending：actor、index、确定的序列化 body/path、outbox 确认边界 through。
2. PUT 批次时用 If-None-Match: *。若网络结果不确定，重启后重用同一 pending 内容和路径。
3. 同名文件返回 412 时 GET 它；完整内容相同可继续，不同则停止并报告身份重复/文件被改写。
4. 用读取清单得到的强 ETag 做 If-Match，合并自己的新 head。清单中的其他 heads、快照描述等必须保留。
5. 412 表示其他客户端先提交了；重读最新清单，只合入自己的 head 后再条件写，不能重放旧清单覆盖别人。
6. 只有发布清单成功，或确认清单已包含这个批次，才清除对应 outbox 和 pending。

~~~mermaid
sequenceDiagram
  participant A as 设备 A
  participant W as WebDAV
  participant B as 设备 B
  A->>W: GET 清单，ETag=e1
  B->>W: GET 清单，ETag=e1
  A->>W: PUT 不可变批次 A12
  B->>W: PUT 不可变批次 B9
  A->>W: PUT 清单 If-Match:e1，加入 A12
  W-->>A: 成功，清单变为 e2
  B->>W: PUT 清单 If-Match:e1，加入 B9
  W-->>B: 412
  B->>W: 重读 e2，保留 A12，再加入 B9
  B->>W: PUT 清单 If-Match:e2
  W-->>B: 成功，两个来源都保留
~~~

一台设备本轮最后读清单以后，另一台还可能继续写；这不是失败，下次检查补齐即可。需要等待确定的一组操作全到齐时，应以明确的 heads/事件集合为验收目标，而不是不断追求“整个云此刻绝对没有新写入”。

### C. 同一数据库多个窗口

同步会话需要本地互斥，业务编辑仍可继续入队。参考实现使用事务租约：随机 token、到期时间、每次请求前验证/续租，结束时仅由持有者释放。示例时长 2 分钟；这不是整个云的锁，也不能用它串行化所有设备。

网页可以结合 Web Locks，但持久租约仍有助于进程崩溃恢复。纯浏览器的多标签页数据库事务必须正确处理并发，不能只靠某一个 JS 内存布尔值。

## 8. 快照、校验与新设备加入

快照包含所有当前保留的字段版本、删除标记和所覆盖的各来源游标，不能只导出界面上可见的业务 JSON。否则离线修改、删除或未解决冲突会在新设备上失真。

生成方法：记录起始 data_revision 与游标；分页读取记录，检查业务版本没有变化；分片压缩上传；所有片段成功后才条件登记快照描述。仅续租等元信息变化不应使快照失败。快照文件在登记前都是不可变的未发布对象。

本项目 SHA-256 针对**解压后的 UTF-8 JSON 原文**，不是 gzip 文件本身。下载方先检查长度、解压上限、epoch/snapshotId/哈希，再应用。

加入方将快照版本与本地版本合并，保留本地 outbox。所有分片处理成功后才推进到快照覆盖的游标，再补之后的批次。本实现逐片合并，失败时已合并的记录可能存在，但快照游标不会提前推进，重试可重放；如果产品要求整个快照对 UI 原子可见，应先写临时表再切换。

### 多年数据的清理策略

当前参考实现会产生新快照，但**不自动删除旧云批次、旧快照或删除标记**。这避免错误清理，却会累积文件和空间。要复用到多年数据，必须把保留策略作为一个独立、需要测试的协议扩展，不能简单按文件年龄删除。

若实现云端日志回收，至少需要：

- 清单中持久且单调前进的回收水位；它不得超过已完整发布并验证可用的快照覆盖范围。
- 所有客户端识别该水位：落后客户端先取快照，即便只落后少量批次也不能再假设旧批次仍存在。
- 下载过程中发现批次/旧快照片段被清理时，重读清单并安全转入新快照；不能跳过缺失数据。
- 条件写阻止迟到的旧快照把清单重新指回已删除数据；保留恢复窗口并处理失败的垃圾清理任务。
- 删除标记不能仅随日志一起消失。要真正回收墓碑，需要活跃设备确认策略、明确退役长期离线设备，或新的 epoch/重新加入协议，防止旧数据复活。

这些扩展在本项目尚未实现。不要在其他客户端未支持水位/重新加入协议时提前启用清理。

## 9. 坚果云 WebDAV 的实际适配细节

| 事项 | 处理要求 |
| --- | --- |
| 端点与账号 | https://dav.jianguoyun.com/dav/ ，登录邮箱 + 第三方应用密码 |
| 首次父目录缺失 | 实测 GET 可返回 409；先 MKCOL 建父目录及 v2，再 GET 清单；建完仍不是预期响应则停止 |
| 不存在的文件 | 已有父目录时通常为 404；不要把 401/403/任意错误都当成空目录 |
| MKCOL 已存在 | 允许服务约定的已存在响应，本项目接受 405；不要忽略其他错误 |
| 清单并发保护 | GET 必须得到可用于 If-Match 的强 ETag；弱 ETag 或缺失时停止写入 |
| 创建文件 | If-None-Match: *；实际观察到并处理了 412 |
| 空闲检查 | If-None-Match: 上次 ETag；304 使用对应的缓存清单，不下载业务批次 |
| gzip | .json.gz 的 body 由应用主动压缩；不是把整份数据库交给云端自行做增量 |
| Android 扩展方法 | 部分 HttpURLConnection 实现不接受 MKCOL；使用支持 WebDAV 方法的 HTTP 库，或经过校验的适配器 |
| 身份验证与 TLS | 凭据加密存储，校验证书与主机名；不要用关闭证书验证来解决连接问题 |
| 请求限速 | 401/403 等待修正配置；429/网络失败退避，支持服务 Retry-After 更好；不要立即循环重试 |
| 请求重定向 | 不把带 Authorization 的请求自动转发到未知主机 |

本项目的真实六客户端测试产生过 20 次条件写 412，最终收敛；无变化时验证了单次 GET 返回 304。测试脚本有意控制频率，不能据此声称已测出任何套餐的最大 QPS、日调用额度或所有网络条件。限额以账号和当时服务规则为准。

## 10. Android 与网页的调度和资源预算

参考默认值如下，是可调的产品取舍，不能直接作为所有应用的性能承诺：

| 项目 | 参考实现 |
| --- | --- |
| 进入前台 / 恢复联网 | 约 2 秒后检查 |
| 前台空闲 | 约 5 分钟 + 少量随机间隔 |
| 连续本地编辑 | 约 15 秒合并调度，并等待撤销窗口结束 |
| 后台或离线 | 暂停新同步工作；在途单个请求可能收尾 |
| 失败 | 指数退避，上限约 30 分钟 |
| 每批 | 最多 500 个事件，目标约 384 KiB 未压缩内容 |
| 单轮 | 收发分阶段各有限额；参考每阶段 12 批，推送后可能再拉一阶段 |
| 本地发送保护 | 单批生成超过约 1 MiB 则停止，需要缩短异常大记录 |
| 传输保护 | 单文件压缩/解压边界均有上限，参考 8 MiB |
| 同步唤醒 | 不使用常驻服务、同步唤醒锁或后台唤醒闹钟 |

本参考引擎有推送前和推送后两次拉取阶段，所以不能把 maxBatches=12 误解为整个同步调用绝对只会 GET 12 个批次；快照分片也需要计入资源预算。移植时建议增加整个会话的总字节和耗时预算。

前台策略意味着后台数据不会实时更新；恢复前台后接续。如果产品确实需要 Android 后台更新，可使用受系统调度的 WorkManager、网络约束和合理间隔，并重新验收耗电，不把高频定时器藏进常驻服务。纯网页的后台计时器同样会被浏览器限制。

只对变化的实体做数据库操作；使用有界分页、按需查询、流式压缩/解压、单同步会话和合理 HTTP 连接复用。快照频率最好结合数据规模、变化量和网络条件设计；“每 64 批一次”是参考触发值，不是无条件适用于百万条数据的最优值。

## 11. 平台适配接口与开发顺序

先隔离三个接口，再接业务 UI：

~~~text
DatabaseAdapter
  inspect(keys) -> meta + rows
  readProjection / page / conflicts / outbox
  commit(expectedRevision, newMeta, changedRows, addedEvents, ack)
  # commit 内部是真正的原子事务

WebDavAdapter
  request(method, relativePath, body?, etag?)
    -> status, responseBody, responseETag
  # 负责认证、TLS、超时、gzip、长度限制，不做业务合并

ReplicationEngine
  localEdit(changes, observedContext)
  applyRemote(events, cursorUpdate)
  sync(scope, shouldContinue, budgets)
    -> partialOrComplete, uploaded, downloaded, conflicts
~~~

| 开发阶段 | 完成判据 |
| --- | --- |
| 记录模型与稳定 ID | 字段规范化、删除、引用、排序规则已定义 |
| 本地存储 | 实体和 outbox 同事务；崩溃重开不丢待发送事件 |
| 两端协议 | 条件写、重放、断线后重用 pending 可验证 |
| 六端与冲突 | 不同字段、同字段、删除和离线编辑都收敛 |
| 快照与升级 | 新设备和旧协议有明确处理，不丢本地未上传内容 |
| 平台网络与凭据 | 真实 WebDAV 及真实 APK 收发通过 |
| 资源预算 | 报告完整进程组 PSS、CPU 时间、实际网络字节和真机功耗边界 |
| UI | 显示部分完成、错误、冲突、尚未上传数量；清楚说明后台策略 |

本地旧 JSON 迁移要在独立副本先验证，导入成功才切换权威存储，旧文件原样保留。旧云协议升级时先保存旧文件的不可变副本，再条件写入旧客户端明确拒绝的标记，最后初始化新清单。必须先验证旧客户端确实会拒绝标记；仅改变文件名不能阻止旧设备继续写另一个旧数据源。

## 12. 必须能够复现的故障矩阵

| 场景 | 必须得到的结果 |
| --- | --- |
| 六端同一周期先后新增/修改 | 所有来源可补齐，最终业务记录一致 |
| 两端同时登记清单 | 一个可能 412；重读合并后双方 head 都在 |
| 批次 PUT 成功、清单 PUT 前退出 | 重启复用 pending，不生成同名不同内容 |
| 清单成功、客户端没有收到响应 | 下次识别已发布进度，不重复创建业务记录 |
| 收到批次但本地事务失败 | 记录和游标一起回滚 |
| 中间批次 404/损坏 | 不跳游标，保留本地待发内容 |
| 同字段并发 | 保留多版本，显式选择后所有端一致 |
| 删除 + 离线修改 | 不自动复活；有明确恢复流程 |
| 快照某片缺失/校验失败 | 不提前推进快照游标，重试不丢本地内容 |
| 两个窗口同时同步 | 同一数据库只有一个发送者，编辑仍可入队 |
| 切账号 / 切目录 / 恢复旧备份 | 不串账号，不误用旧 pending 或克隆身份 |
| 无变化 / 进入后台 | 前台条件检查有界，后台策略与流量实测相符 |
| 弱 ETag、401、429、超限压缩包 | 停止错误覆盖，有可恢复状态和退避 |

可参考 [真实 WebDAV 验收程序](../scripts/verify-webdav.mjs)、[协议回归测试](../tests/delta-sync.test.mjs)及 [Android 测试指南](android-testing.md)。模拟测试证明设定故障下的行为；真实服务测试证明本次服务适配；模拟器测试不能替代实体手机耗电。

## 可交给其他 IDE 的实现任务

> 根据本指南为目标应用设计本地记录与版本表、持久 outbox、每来源连续游标及平台数据库事务适配。为应用创建独立云目录和明确的协议版本。实现不可变批次 + 强 ETag 条件清单，保存 pending 后上传，登记成功才确认 outbox；正确处理真实坚果云缺少父目录的 409、并发 412、空闲 304。用稳定 ID、因果字段版本、删除标记与冲突选择实现合并，再实现分片快照。先通过故障矩阵和六端模拟测试，再在独立真实云目录、真实 Android APK 上验证。报告具体性能测量口径与未实现能力。不要把正在使用的 SQLite 文件放进多设备同步目录，不要将密码写入源码、命令参数或报告。
