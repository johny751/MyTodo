## 建立一致性点和清单

**已有源码证据。** 三端账本声明 WAL 模式和 `synchronous=FULL`。Windows 的数据位置迁移对 `.sqlite` 使用 SQLite backup API，跳过 WAL、SHM 和旧 journal 文件，随后执行 `integrity_check`。A 没有运行证据说明 SQLite 与所有账本旁文件、Android Feedback Kit 图像或 Web/系统偏好能取得同一恢复点。[Windows 位置迁移](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/windows-storage-inventory.md#L151-L158) · [盘点缺口](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/inventory-open-questions.md#L7-L19)

**设计建议。** 以下顺序定义完整候选的证据要求，每次独立分配 `backupId` 并指定范围。

1. 声明需要一致的账号、文件和模块，识别前后台 writer，完成已批准的停写或等效屏障。等待在途 SQL、同步、反馈保存与附件状态提交完成或明确撤回，保留其结果。冻结期间记录账本路径/文件身份、快照句柄、写入代次、schema 指纹、`revision/dataRevision`、Actor 和作用域。旧库缺独立 DB ID 时记录已有身份见证，无法证明身份的候选不能标为同库。哈希可证明特定快照字节，独立于逻辑账本 ID。
2. 从 SQLite 支持的一致读点采集独立快照，包含该快照可见的已提交 WAL 内容。不得用互不协调的主文件和 sidecar 的复制作为成功证据。原库依然活跃或恢复标记不明时，保留原件及日志，不通过移除 WAL/SHM、清理 pending 或强行 checkpoint 丢失信息。反馈数据库与账本执行各自一致性读，但应在共同的写入冻结窗口取关联模块及内容文件，或为每个模块记录各自已证明的时间点与限制。发现关联模块无法提供同一停写屏障时，明确降为分模块备份。
3. 清单建议记录 `backupFormatVersion`、`backupId`、创建时的 UTC 时刻、应用与源版本、恢复类型、组件/账号/安装/namespace 及作用域映射、已有身份标记、schema/contract 识别结果、资产引用、采集完成边界及文件条目。每个条目标记逻辑相对路径、用途、能否缺失、字节数、对原始包内字节的 SHA-256、原载体类型和关联对象。文件缺失、损坏、未取、可重建要用明确原因。原始逐字段证据保留值类型和缺席/null，摘要索引只能用于查对。远端证据中的 ETag、兼容内容摘要和本地 `pending.body` 摘要应注明各自的字节输入，区别未压缩正文与 gzip 文件字节。
4. 在临时位置检查 SQLite 快照、记录和文件引用闭合，校验清单所列每件对象。资产包含证据已支持的版本/ID、散列、预期 MIME、大小和原始字节。压缩包须限制总大小、解压条目数与单条大小，拒绝重复条目、越界路径和链接逃逸。对可重建索引记录版本和出处。校验通过并持久化完成凭证后才发布完成备份，生成中断不得覆盖上一份完整包。清单的 SHA-256 只用于完整性，应有独立可信清单锚点或授权来源机制后才接受外来恢复包。

**尚待设备验证。** 验证活动 WAL 中已提交记录被包含、未提交记录隔离、并发写入确认、复制进程中止、commit/磁盘满/文件替换故障与重启后分支。Windows 跨卷和系统占用文件、Android SAF 和权限、Web origin 和浏览器写入、真实设备 OS 和存储的持久化保证均需后续验证。进程中止与物理断电的证据分别记录。

**需要负责人决策。** 确认停写窗口、包格式及受信任清单机制、加密和访问策略、指定账号/整机默认模式、保留数量和容量、不可协调组件单独降级的规则。[现有验证计划 D01–D06](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/validation-plan.md#L74-L89)

## 恢复的执行顺序与失败行为

| 步骤 | 设计建议 | 核验与失败处理 |
| --- | --- | --- |
| 1. 识别介质与授权范围 | 在停用外部同步和通知的隔离区读取清单，确认来源、恢复对象、账号/namespace、账本身份约束、受支持的备份及数据库版本。保存现有账本和旁文件的恢复点 | 库不明、错账号、错来源、超限及损坏时保存原件与首错，停止进入可写恢复。只存在业务 JSON 时可转显式业务交接评估 |
| 2. 逐件校验并暂存 | 在隔离目录重新计算哈希及大小，记录准确缺项。恢复 SQLite 主账本与其复制基础设施，一并暂存所需账号元信息、独立本地组件和图片。对读入的异常原值生成报告，保持源数据只读 | 数据库、队列或必需模块缺件时，候选留在隔离区。可选模块仅在事先定义独立边界且用户知晓缺失的条件下跳过。已存在故障原件不能被新暂存结果覆盖 |
| 3. 同一候选重开和内容核对 | 以新进程重开暂存候选的原指定路径。记录原库、候选库和恢复模式的可核验身份。检查数据库完整性、适用约束、源/目标 schema、业务 ID、层级、时间值和原存在状态、墓碑、冲突、现存字段历史。核对 `pending.body` 等原字节，复算资产、图片引用和反馈组件 `restore_generation` | `integrity_check` 仅覆盖 SQLite 完整性的一部分。出现逻辑 ID、时钟、列投影、历史或引用不一致时不得完成恢复。以新空库或者变更 Actor 的通过结果量度独立场景 |
| 4. 安全切换和验证启动 | 审批及停写仍有效时，通过可回退的一致入口切换到候选，保留原目录和切换标记。数据打开、路径、目标账号、Actor/范围及模块的离线检查通过后，才可按计划逐步恢复用户可见的本地行为。运行锁和共享 URI 由本机重建，派生索引在版本可证时重建 | 切换之前失败，原工作集继续留在原身份。切换后且未有新的写入/外部副作用时，可将入口指回已核验的原状态。已有写入或可能产生外部副作用时，两份状态连同日志保留，冻结并人工对账。未知 COMMIT 或切换结果先判明路由及 durable marker，禁止盲目重做 |
| 5. 独立决定同步开关 | 同步开启需要独占旧 Actor、远端作用域、epoch 和进度的独立证据。缺凭据、旧库身份不明或 remote head 不可核对时，保留离线副本和未投递队列。提醒/番茄钟恢复要另判定是否可重新调度或提示 | 保留首次错误、路径/身份、恢复阶段、返回码及每次重试结果。已发布的远端对象须在其作用域对账，不能以本地指针回退抵销远端发布 |

**设计建议。** 后续经授权后，T15 应覆盖备份、DDL、回填、迁移登记、事务提交前后及文件切换边界。每个故障留下原始路径、稳定身份、首错和持久状态。重启同一测试路径后，判断升级前或升级后完整状态，证明重复启动不会重复执行同一迁移。T16 应对每种明确支持的旧版本分别证明 ID、时间、关系、墓碑、冲突、原始记录、已确认的恢复证据、未确认队列和同步 meta 的保留。验证视图及源字节两层保真，注明派生内容允许的重建及已声明的损失。原库与恢复候选分别验证其预期身份，记录映射和不同 PID 新开结果。旧库样本只能用经授权的类别和范围。

**尚待设备验证。** 本批只有设计。T15/T16 执行、SQLite/文件系统耐久性、三端真实封装和设备同库恢复需要独立运行证据。历史运行只能说明报告里的已覆盖情境。[阶段 0 Android 风险](../phase0-final-review/android-stability-risk.md)

**需要负责人决策。** 确认最终必须支持的旧格式样本和设备/环境范围、可接受的显式损失、恢复验收人和阻断条件。未达生产条件的工作继续留在离线设计和等待审批状态。[迁移与版本契约草案](migration-versioning-contract.md)
