## 建立一致性点和清单

**FACT（已有源码证据）。** 三端账本声明 WAL 模式和 `synchronous=FULL`。Windows 的数据位置迁移对 `.sqlite` 使用 SQLite backup API，跳过 WAL、SHM 和旧 journal 文件，随后执行 `integrity_check`。A 没有运行证据说明 SQLite 与所有账本旁文件、Android Feedback Kit 图像或 Web/系统偏好能取得同一恢复点。[Windows 位置迁移](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/windows-storage-inventory.md#L151-L158) · [盘点缺口](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/inventory-open-questions.md#L7-L19)

**PROPOSAL（设计建议）。** 以下顺序定义完整候选的证据要求，每次独立分配 `backupId` 并指定范围。

1. 声明需要一致的账号、文件和模块，识别前后台 writer，完成已批准的停写或等效屏障。等待在途 SQL、同步、反馈保存与附件状态提交完成或明确撤回，保留其结果。冻结期间记录账本路径/文件身份、快照句柄、写入代次、schema 指纹、`revision/dataRevision`、Actor 和作用域。旧库缺独立 DB ID 时记录已有身份见证，无法证明身份的候选不能标为同库。哈希可证明特定快照字节，独立于逻辑账本 ID。
2. 从 SQLite 支持的一致读点采集独立快照，包含该快照可见的已提交 WAL 内容。不得用互不协调的主文件和 sidecar 的复制作为成功证据。原库依然活跃或恢复标记不明时，保留原件及日志，不通过移除 WAL/SHM、清理 pending 或强行 checkpoint 丢失信息。反馈数据库与账本执行各自一致性读，但应在共同的写入冻结窗口取关联模块及内容文件，或为每个模块记录各自已证明的时间点与限制。发现关联模块无法提供同一停写屏障时，明确降为分模块备份。
3. 清单建议记录 `backupFormatVersion`、`backupId`、创建时的 UTC 时刻、应用与源版本、恢复类型、组件/账号/安装/namespace 及作用域映射、已有身份标记、schema/contract 识别结果、资产引用、采集完成边界及文件条目。每个条目标记逻辑相对路径、用途、能否缺失、字节数、对原始包内字节的 SHA-256、原载体类型和关联对象。文件缺失、损坏、未取、可重建要用明确原因。原始逐字段证据保留值类型和缺席/null，摘要索引只能用于查对。远端证据中的 ETag、兼容内容摘要和本地 `pending.body` 摘要应注明各自的字节输入，区别未压缩正文与 gzip 文件字节。
4. 在临时位置检查 SQLite 快照、记录和文件引用闭合，校验清单所列每件对象。资产包含证据已支持的版本/ID、散列、预期 MIME、大小和原始字节。压缩包须限制总大小、解压条目数与单条大小，拒绝重复条目、越界路径和链接逃逸。对可重建索引记录版本和出处。校验通过并持久化完成凭证后才发布完成备份，生成中断不得覆盖上一份完整包。清单的 SHA-256 只用于完整性，应有独立可信清单锚点或授权来源机制后才接受外来恢复包。

**UNVERIFIED（待验证）。** 验证活动 WAL 中已提交记录被包含、未提交记录隔离、并发写入确认、复制进程中止、commit/磁盘满/文件替换故障与重启后分支。Windows 跨卷和系统占用文件、Android SAF 和权限、Web origin 和浏览器写入、真实设备 OS 和存储的持久化保证均需后续验证。进程中止与物理断电的证据分别记录。

**OWNER DECISION（负责人决策）。** 确认停写窗口、包格式及受信任清单机制、加密和访问策略、指定账号/整机默认模式、保留数量和容量、不可协调组件单独降级的规则。[现有验证计划 D01–D06](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/validation-plan.md#L74-L89)

## 恢复的执行顺序与失败行为

| 步骤 | PROPOSAL（设计建议） | 核验与失败处理 |
| --- | --- | --- |
| 1. 识别介质与授权范围 | 在停用外部同步和通知的隔离区读取清单，确认来源、恢复对象、账号/namespace、账本身份约束、受支持的备份及数据库版本。保存现有账本和旁文件的恢复点 | 库不明、错账号、错来源、超限及损坏时保存原件与首错，停止进入可写恢复。只存在业务 JSON 时可转显式业务交接评估 |
| 2. 逐件校验并暂存 | 在隔离目录重新计算哈希及大小，记录准确缺项。恢复 SQLite 主账本与其复制基础设施，一并暂存所需账号元信息、独立本地组件和图片。对读入的异常原值生成报告，保持源数据只读 | 数据库、队列或必需模块缺件时，候选留在隔离区。可选模块仅在事先定义独立边界且用户知晓缺失的条件下跳过。已存在故障原件不能被新暂存结果覆盖 |
| 3. 同一候选重开和内容核对 | 以新进程重开暂存候选的原指定路径。记录原库、候选库和恢复模式的可核验身份。检查数据库完整性、适用约束、源/目标 schema、业务 ID、层级、时间值和原存在状态、墓碑、冲突、现存字段历史。核对 `pending.body` 等原字节，复算资产、图片引用和反馈组件 `restore_generation` | `integrity_check` 仅覆盖 SQLite 完整性的一部分。出现逻辑 ID、时钟、列投影、历史或引用不一致时不得完成恢复。以新空库或者变更 Actor 的通过结果量度独立场景 |
| 4. 安全切换和验证启动 | 审批及停写仍有效时，通过可回退的一致入口切换到候选，保留原目录和切换标记。数据打开、路径、目标账号、Actor/范围及模块的离线检查通过后，才可按计划逐步恢复用户可见的本地行为。运行锁和共享 URI 由本机重建，派生索引在版本可证时重建 | 切换之前失败，原工作集继续留在原身份。切换后只有证明无新写入/外部副作用，且原库仍等于切换前最新冻结状态时，才可将入口指回该原库；禁止指回更早的历史备份。已有写入或可能产生外部副作用时，两份状态连同日志保留，冻结并人工对账。未知 COMMIT 或切换结果先判明路由及 durable marker，禁止盲目重做 |
| 5. 独立决定同步开关 | 同步开启需要独占旧 Actor、远端作用域、epoch 和进度的独立证据。缺凭据、旧库身份不明或 remote head 不可核对时，保留离线副本和未投递队列。提醒/番茄钟恢复要另判定是否可重新调度或提示 | 保留首次错误、路径/身份、恢复阶段、返回码及每次重试结果。已发布的远端对象须在其作用域对账，不能以本地指针回退抵销远端发布 |

**FACT（已有源码证据）。** 盘点列出原记录、业务投影、pending/cursor 持久化与 Android 本地恢复代次，各组件使用自己的键及写入语义。[复制层字段](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/cross-platform-field-mapping.md#L93-L109) · [反馈还原库和代次](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/android-storage-inventory.md#L125-L156)

**UNVERIFIED（待验证）。** 三端文件系统切换原子性、真实 SQLite 封装、同一库路径在应用重启后的身份和字段一致性，以及恢复中断后是否保留并识别上一状态。Android issue #1 现存证据仍 `OPEN RISK`。[Android issue #1](https://github.com/johny751/MyTodo/issues/1)

**OWNER DECISION（负责人决策）。** 确认恢复批准权、原件及失败副本保留、允许离线部分恢复的组件、不能继续恢复时由谁决定对账和后续操作。

| 原设备续传 | 本地 `actor` 参与事件及 batch 身份。应用未有通用设备撤销/换代账本，Windows 迟到响应与会话交接仍待查 | 逐项证明原账本、身份、相同 scope/epoch、新进程与旧会话完全隔离。切换前冻结旧库及旧设备写入与自动重试，处理已在途请求。凭据的隔离授权、会话排他和进度对账均需独立证据。如果旧副本或丢失设备无法确认停写，候选只能离线。未来若另行实施栅栏，应使状态写入同时验证当前会话代次、范围和操作身份 | Windows 旧请求迟到后可能提交的 ACK、缓存、游标等，恢复与前后台进程隔离，真机重启和网络恢复 | 原 Actor 恢复所需证明、谁有授权停用原设备、无法隔离时采用何种新设备接续路径 |
| 较旧且仍有待提交状态的备份 | `outbox.id` 与 `meta.pending.through` 关联本地前缀，pending 原 `body` 是重试内容，`cursors` 记录批次而 `vector` 记录事件序号。manifest heads 表达远端批次高水位 | 先对照原队列有序前缀与正文所含事件/身份/内容及路径。相同 scope/epoch 的远端头已覆盖时，还需能够证明同一批次内容及其发布效果，再由原协议走正常确认。在形成新事件或批次前，需证明 `seq`、批次号和相关向量相对全部可核验已用身份安全递进。缺批、历史已裁剪、身份相同但内容不同、旧份与当前线上进度无法对账时均保持隔离，未确认状态与后续编辑继续留存。只凭本地 cache、已存在路径或 head 数字无法确认恢复队列可安全清理或下一事件身份可用 | 同库重开、重试原字节、丢失发布响应、远端 epoch 变更、脏/缺 pending、确认失败后的 later-event 保留，以及旧 `seq` 不得复用 | 可接受何种远端收据证据，远端已无法重查时是继续保留旧离线队列还是提交人工检视 |
| 换机或新账本 | 阶段 0 区分新库新 Actor 观察者与原库恢复。业务 JSON 可交接活体数据，无法证明已无待提交编辑或历史 | 新身份用明确的新设备流程，从授权的可信集合同步并重新核对主账本。旧备份作为只读证据，不直接克隆 `actor/seq` 或搬运待发原正文到另一 scope。未发布旧编辑的任何补入先保留来源并人工决定，若获批，用新身份显式记录重新提出的编辑 | 履历、墓碑、恢复使用新身份/原身份的区别，各设备的同期可重复恢复；迁移旧未投递记录如何保全 | 新设备恢复条件，不能自动映射未发布事件时的回收期限与审查人 |

证据见 [A 盘点 pending、manifest 与游标](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/cross-platform-field-mapping.md#L95-L108) · [阶段 0 同步安全](../phase0-final-review/sync-safety-review.md#历史版本设备丢失和恢复) · [所有权边界草案](data-ownership-and-sync-boundaries.md)。

## 本候选补充：备份之后的新进展与降级阻断

**FACT。** 已确认的 ACK 可在本地事务中推进游标、清除 pending 并物理删除 outbox 前缀；实体复制记录还会压缩已被支配的字段候选。因此“当前 outbox 比备份少”不表示当前库可被旧备份替代，较新远端 head 也不能证明旧 pending 可直接重用。[阶段 0 ACK/合并边界](../phase0-final-review/sync-safety-review.md#事务发布和重放) · [A 的计数、队列与 pending 字段](https://github.com/johny751/MyTodo/blob/6a4b179f361602f47429bc9aa88e51c0b61395e3/docs/upgrade/d1-01/cross-platform-field-mapping.md#L97-L108)

**PROPOSAL。** 区分三个时点：`B` 是指定备份的一致性点，`S` 是恢复或迁移前最新停写点，`A` 是候选切换点。任何恢复覆盖或回退决策必须比较目标当前状态与 `S`，并比较 `S` 相对 `B` 的新进展。只验证备份自身的哈希不构成可覆盖当前库的资格。备份时间戳用于记录，不作为“没有新进展”的证明。

| 断言 ID | PROPOSAL：必须保留并比较的输入 | BLOCKER：拒绝覆盖/直接回滚条件 |
| --- | --- | --- |
| BR-01 身份 | 实际解析路径、文件/快照身份见证、账号/组件/namespace、Actor、scope、epoch、原库与候选的映射、冻结代次和进程身份 | 同一路径已换文件、错账号/组件、Actor 或范围不符、标记不完整、旧 writer/在途会话未排除、无法判明活动指针 |
| BR-02 业务/事件 | `entities` 所有行及 SQLite 类型、原 `data/record/conflicts/deleted`、原值存在性、已保留事件身份及内容，`revision/dataRevision/clock/seq/vector`；对缺失或压缩内容保留未知说明 | `B→S` 出现新增、修改、删除、冲突变化或事件/逻辑计数推进；仅活动业务 JSON 相同而复制证据不同；计数未变但底层行或原字节改变；是否有新事件不可判定 |
| BR-03 队列/ACK | 原 outbox 有序 `(id,event)` 全集、pending 原 `body/path/device/index/through`、cursors、queue、cachedManifest 与其来源资格；同时保留明确 ACK/提交证据 | 新待发记录、ACK 后队列前缀减少、pending 被清或换代、cursor 推进、同身份异内容；队列减少但没有因果可核对的 ACK 记录；不能完整关联 pending 正文和队列 |
| BR-04 远端进度 | 同 scope/epoch 的受信任 manifest/head、批次正文身份及摘要、快照游标、ETag 和观测边界；本批只用合成远端证据夹具 | `B→S` 远端发布/接收有新进展、epoch 改变、旧 Actor 已用更高 seq/batch 编号；证据陈旧、缺批、头数字无正文证明、真实远端当前状态未获授权核验。无法核验时只保留离线候选，禁止恢复同步发送 |
| BR-05 本地组件/原图 | 反馈四表、草稿、软删除/撤销引用、`restore_generation`、图片原件的长度和 SHA-256；提醒发送/延后回执、番茄钟持久状态及其他必需组件各自的一致性点 | 备份后反馈/图片/回执/聚合发生变化、必要原图缺失或字节不符、模块一致性点不相容；用缩略图/重编码图代替原图；由旧状态恢复会重复通知或覆盖后续本地数据且没有独立处理决定 |

**PROPOSAL。** 检测新进展时不自动清理 outbox，不增补 seq，不重新编码 pending，不制造事件，不覆盖当前数据库来“使比较通过”。新进展存在时保存 `B/S/A` 与首次阻断报告，原工作集不变；后续只能在另批授权下进行保留来源的前向恢复或人工对账。显式有损业务交接仍是独立副本，不获得原 Actor 连续性或旧文件覆盖资格。新 Actor 场景独立保留旧未投递编辑，不用新身份掩盖旧身份检查失败。

## 本候选补充：失败矩阵与一致性证据

| 边界 | PROPOSAL：允许动作 | BLOCKER：禁止动作 |
| --- | --- | --- |
| 备份/暂存/转换中失败，尚未激活 | 保留原库、旁文件、原图、既有活动入口及首错；隔离候选并记录是否 commit 未知；重新打开同一指定候选核验 | 以新空库/新 Actor 重跑替代故障候选；清 WAL/SHM/pending；提前改活动入口；用更早备份恢复正在使用的原库 |
| 激活提交或入口切换结果未知 | 冻结所有 writer，读回 durable marker、实际路由和组件代次，保全两侧，确认处于完整 `S` 或完整候选态 | 按预期结果假定 commit 成功/失败；盲目重做或切回；只检查目录名与存在性 |
| 激活后证明无新副作用 | 仅在 `S` 原库身份和组件状态仍完整、活动候选没有新数据/ACK/通知/发布的证据下，按受审切换计划返回 `S` 原库 | 降回 `B` 或任意更早快照；没有 side-effect 日志即当作没有副作用；仅回退 DB 而遗漏图像/反馈代次 |
| 激活后有新写入或任何外部副作用 | 冻结两侧，保留新数据、ACK、通知/图片提交和远端效果，进入前向恢复/对账 | 自动降级到旧库、覆盖新进展、撤销已发远端 batch 或复用旧 seq，宣称本地回滚已撤销外部发布 |

**PROPOSAL。** 精确跨文件备份的证明必须包含共同停写屏障、每个 SQLite 快照的读点/采集完成凭证及原图复制窗口。核心库、反馈库和内容文件没有共同屏障时可保存多个分模块快照，但不得标为跨组件精确恢复包。每件图像有原件输入路径、字节数、SHA-256；观察用缩略图单列为派生物，其 hash 与像素尺寸不替代 `originalContentSHA256`。稳定 ID、URI、标题或图像显示正常都不能证明原件字节完整。

**UNVERIFIED。** BR-01–05 和失败矩阵的实际用例结果由本批工具报告引用，本文不填预期通过数。合成 SQL、文件、remote progress 夹具只证明受测工具的拦截逻辑；不能证明 Android SAF/Keystore、Windows 文件切换/DPAPI、真实网络、fsync 断电或三端生产封装。Android issue #1 和 A 的 `UNKNOWN/NEEDS INVESTIGATION` 保持开放。

**OWNER DECISION。** 生产恢复必须另行确定支持版本、组件必需集、writer 排他证明、真实远端核验范围和前向对账责任。D1-02 准备工具不授予旧文件覆盖或生产迁移权限。[独立工具准备设计](d1-01-02-tool-preparation-design.md)
