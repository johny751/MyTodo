**建议 `CONDITIONAL-GO`。** 由项目负责人明确批准后，仅开放 D1-01 和下列隔离工作。现有三端协议和故障验收足以支持契约工作。当前只有单目标 ACK，Windows 迟到响应与租约接管交错缺少验证，Android 首次进程异常仍存在，三端一致备份及编号迁移未验收。这些条件限制可写入的范围。

### 开工前与下一轮准入

1. 负责人记录批准的子任务、允许的 GitHub 环境、回退责任人、保持禁用的入口，并接受 Android #1 开放与单 WebDAV 范围。没有该记录时 D1 继续暂停。开工时应核对当前提交相对本审查基线仅有文档差异，或对实际变化重审。测试库与生产账号、生产 WebDAV 和用户数据隔离。
2. D1-02 云端候选进入下一环节前验证三端真实存储写入与指定数据库身份。明确列名、CAS、旧字段默认值、事件和队列一致性都应有机器回执。ADB/SQLite 故障夹具只能在项目授权的 GitHub 环境执行。
3. 任何生产迁移入口接通前，完成一致备份与恢复、旧 schema 识别、维护期全部 writer 停写、编号与 checksum 登记、未知 schema 保留并拒绝。T15 需覆盖备份、DDL、回填、登记、事务提交前后及文件切换，证明重复启动不重复迁移。T16 对每种支持旧版保全 ID、关系、时间、墓碑、冲突、事件、队列和同步 meta。三端均以同库身份和新进程重开为证据；失败须留原路径和首错。
4. 任何扩大同步并发或迁移与同步交叠前，补 Windows 延迟响应＋租约接管验证，证明过期会话的 ACK、缓存或游标提交不会影响新会话。目标账本支持每个目标独立的交付状态后，再测顺序互换、部分失败、单目标离线、删除与重复投递；只有所有应收目标持久确认才允许回收事件。需要能回退到单目标运行。
5. Android 生产库写入准入须能追踪首次启动、指定库路径、actor 与重启后的 rows/meta/outbox。对相同依赖终止做定向归因与同库恢复；换新库只能作为独立接收场景。正式发布前由负责人以证据关闭 #1 或明确接受残余风险，要求真实设备稳定性与签名覆盖升级记录。

| 尚未完成的验证 | 放行点及可核对结果 |
| --- | --- |

| 正式签名 APK 覆盖升级 | 正式发布前置。以实际签名谱系、递增 versionCode 和旧签名版本安装升级验证数据与复制身份。 |
